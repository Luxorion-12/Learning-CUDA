# MXFP8 / NVFP4 低精度软件模拟与反量化

> 初步总结报告。本文已整理实现方案、正确性方法和八轮优化历程；提交前还需用最终默认 CLI 统一重跑正式误差、带宽、CPU 对照和 profiler 数据。

## 1. 项目目标

本项目在不依赖原生 FP8/FP4 指令的普通 NVIDIA CUDA GPU 上，实现 MXFP8 和 NVFP4 的软件量化与反量化。程序读取 FP32 或 FP16 行主序矩阵及量化参数文件，在 GPU 上完成 scale 计算、低精度编码、NVFP4 四位打包、解包和反量化，并输出低精度权重、FP16/BF16/FP32 恢复张量、误差指标及性能日志。

CPU reference 用于定义数值语义和充当 CUDA 结果 oracle；正式计算路径由 CUDA kernel 完成。当前实测设备为 NVIDIA GeForce RTX 3050 Laptop GPU，Compute Capability 8.6，CUDA Toolkit 12.8。

## 2. 低精度格式与数值规则

### 2.1 MXFP8

MXFP8 每 32 个连续元素共享一个 E8M0 scale，每个归一化元素保存为一个 E4M3 编码字节。行主序矩阵先连续展平，量化块允许跨越行边界。

对块内最大绝对值 `amax`，选择能够覆盖该块动态范围的 E8M0 scale `S`：

```text
q_i = encode_e4m3(x_i / S)
x_hat_i = decode_e4m3(q_i) * S
```

block mode 每 32 个元素保存一个 scale；tensor mode 整个张量共享一个 scale。

### 2.2 NVFP4

NVFP4 元素使用 E2M1 四位编码，整个张量共享 FP32 global scale，每 16 个连续元素使用一个 E4M3 local scale。软件实现采用：

```text
G = tensor_amax / (448 * 6)
L_b = encode_e4m3((block_amax / 6) / G)
q_i = encode_e2m1(x_i / (G * decode_e4m3(L_b)))
x_hat_i = decode_e2m1(q_i) * G * decode_e4m3(L_b)
```

两个 E2M1 元素打包进一个字节，高四位保存偶数元素，低四位保存奇数元素；奇数长度最后一个低四位补零。tensor mode 只使用一个 local scale。

### 2.3 舍入

`nearest` 使用最近值与 ties-to-even；`stochastic` 根据相邻两个可表示值之间的位置和固定 seed 选择编码。相同输入与 seed 可复现，不同 seed 能产生不同合法结果。

## 3. 文件和配置协议

输入张量使用固定 20 字节 header：两个 little-endian `int64` 维度和四字节 ASCII dtype，后接 FP32 或 FP16 行主序数据。FP16 输入保留原始二进制位模式，并由 CUDA kernel 原生读取。

量化参数文件支持 `format`、`block_size`、`scale_mode`、`output_type`、`rounding`、`target_gpu` 和可选随机种子。低精度权重文件采用版本化 `LUXQ0001` header，保存格式、矩阵形状、输入/输出类型、scale mode、元素数、global scale、scale 数组和 packed data，可以脱离原输入执行独立反量化。

## 4. 软件架构与执行流程

- `cpu_reference/`：格式编解码、CPU 量化/反量化、文件 IO、配置解析和误差指标。
- `gpu_baseline/`：CUDA kernel、输入生成器、benchmark、正式 CLI 和 CPU/GPU 对照测试。
- `input/`：冻结的 FP32/FP16 测试输入、manifest 和量化配置。
- `optimization/`：v0–v8 独立源码、实验结论和最终对照结果。

正式 CLI 的 `run` 流程为：读取并校验输入与配置，上传原生 FP32/FP16 数据，执行 GPU 量化，保存 `weights.luxq`，执行 GPU 反量化，保存恢复张量并计算误差和性能指标。`dequantize` 流程只读取 `weights.luxq` 并恢复张量。

## 5. 正确性验证

CPU reference 和 CUDA 路径逐层比较 MXFP8 scale/code、NVFP4 global/local scale 与 packed byte、恢复结果及零符号，并覆盖 tensor/block scaling、nearest/stochastic、奇数元素、非整齐尾块、全零、异常值、非法文件和独立反量化。

当前 CTest 共 13 项，全部通过。v8 四个正式流程生成的权重和恢复张量与正确性基线逐字节一致。

## 6. 输入数据与计时协议

冻结输入包含 uniform、normal、outliers、zero-heavy、multiscale 和 `1023×1025` 尾部矩阵，每类同时提供 FP32 与 FP16，共 12 个文件。manifest 记录 seed、形状、dtype、分布和统计量；benchmark 不会自动重新生成输入。

kernel 使用 CUDA event 计时，先 warmup 再重复采样，报告 median 和 nearest-rank p95。文件 IO、显存分配和 CPU oracle 不进入 kernel 时间。正式提交前将统一使用同一协议重跑 v0、v8、CPU reference 和最终误差矩阵。

## 7. Baseline 与瓶颈

v0 的反量化采用每线程恢复一个元素；量化编码器从低到高扫描候选低精度值。Nsight Compute 初步分析表明，相邻线程地址连续，但一字节 code 加载和重复 scale 加载降低了 sector 利用率。更主要的量化瓶颈是 E4M3 最多 126 次、E2M1 最多 7 次的候选扫描。

## 8. 优化方法与迭代历程

所有方向先验证字节级正确性，再与上一最佳版本交错计时。用户指定不设置固定百分比门槛：综合实测更快、核心路径没有有意义回退且正确性不变即可晋级。

最终晋级链：`v0 → v1 → v3 → v6 → v7 → v8`。

| 方向 | 假设与修改 | 结果 | 决策 |
|---:|---|---|---|
| 1 | 扫描64/128/256/512 threads-per-block | 128线程综合约+0.57% | 晋级 |
| 2 | 检查全局内存合并访问 | 地址已连续，问题主要是窄加载 | 无代码候选 |
| 3 | MXFP8每线程读取4个code；NVFP4每线程恢复一个packed byte；向量写回 | 反量化综合约1.53x | 晋级 |
| 4 | shared reduction替换为warp shuffle | 综合约+0.02%，MXFP8轻微回退 | 淘汰 |
| 5 | scale预取到shared memory | NVFP4 block明显回退 | 淘汰 |
| 6 | NVFP4 shared code由byte扩为32-bit，消除bank冲突 | NVFP4 block约+0.023% | 晋级 |
| 7 | 线性候选扫描改为固定7/3步二分查找 | 量化综合约3.55x | 晋级 |
| 8 | 完全展开固定二分步骤 | 在v7上量化综合再提升约3.06% | 晋级 |

### 8.1 失败方案和开发问题

方向3第一次实现把 NVFP4 的 `e2 * global * local` 改写成 `e2 * (global * local)`，数学上等价但 FP32 舍入顺序不同，导致输出哈希变化。该候选没有直接接受，而是恢复原运算顺序后重新执行四类哈希和完整流程检查。这说明低精度软件模拟不仅要比较误差范围，还需要固定计算顺序以保证可复现性。

方向4和方向5虽然减少了同步或全局 scale 读取，但端到端 kernel 实测没有收益或出现回退，因此保留源码和记录而未叠加到后续最佳版本。各方向的完整数据和说明见 `optimization/v*/README.md`。

## 9. 当前最终性能

RTX 3050 Laptop GPU 上，v0/v8 交错运行3轮、每轮预热5次并计时20次的初步结果如下：

| 场景 | v0量化 ms | v8量化 ms | 加速 | v0反量化 ms | v8反量化 ms | 加速 |
|---|---:|---:|---:|---:|---:|---:|
| MXFP8 block / FP16 | 12.328944 | 5.456864 | 2.26x | 0.053248 | 0.036272 | 1.47x |
| MXFP8 tensor / FP32 | 113.272831 | 10.684112 | 10.60x | 0.039936 | 0.025600 | 1.56x |
| NVFP4 block / FP32 | 8.883200 | 1.436048 | 6.19x | 0.046592 | 0.036864 | 1.26x |
| NVFP4 tensor / FP16 | 9.499648 | 7.846768 | 1.21x | 0.039936 | 0.024576 | 1.63x |

四场景几何平均量化约3.66x、反量化约1.47x。最终报告还需加入统一协议下的 p95、GB/s、MaxAbs、MAE、MSE、压缩率和 CPU/GPU 加速比。

## 10. 软件模拟与依赖边界

E4M3、E2M1、E8M0 编解码、scale 选择和四位打包均由普通 CUDA C++ 软件实现；没有使用原生 FP8/FP4 Tensor Core，没有依赖 Transformer Engine。FP16 是正式 GPU 输入类型，BF16/FP16/FP32 是反量化输出类型。`target_gpu` 只进入报告，不会切换硬件专用实现。

## 12. 构建与复现

默认只构建正式程序和测试；历史源码始终保留，但仅在显式开启时编译：

```powershell
cmake -S . -B build/cuda -G "Visual Studio 17 2022" -A x64 `
  -T "cuda=C:\Program Files\NVIDIA GPU Computing Toolkit\CUDA\v12.8" `
  -DLUXORION_ENABLE_CUDA=ON -DCMAKE_CUDA_ARCHITECTURES=86
cmake --build build/cuda --config Release
ctest --test-dir build/cuda -C Release --output-on-failure

# 复现v0-v8时追加：-DLUXORION_BUILD_HISTORY=ON
```

正式量化及独立反量化：

```powershell
.\build\cuda\Release\luxorion_cli.exe run `
  input\benchmark\normal_fp16_1024x1024_seed1234.tensor.bin `
  input\quant.cfg output\run_example

.\build\cuda\Release\luxorion_cli.exe dequantize `
  output\run_example\weights.luxq `
  output\run_example\restored_again.tensor.bin
```
